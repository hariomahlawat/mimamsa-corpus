## 1. Identity model

| Entity | What it is | Key in the register |
| --- | --- | --- |
| **DOCUMENT_COPY** | One stored byte file. Different bytes mean different copies, even when the content is the same. | `sha256` |
| **JUDGMENT** | One decision: a judgment or order pronounced by a court on a date, by a bench. A common judgment that disposes of 40 connected petitions is **one** judgment. | `judgment_key` (`JK-` plus the first 16 hex digits of the lowest sha256 among its copies) |
| **PROCEEDING** | A case disposed of by the judgment (writ petition, appeal, application). One judgment can dispose of many proceedings. One proceeding can have several judgments over time. | `proceeding_keys_meta` (court code and crawler case number); `proceeding_keys_text_candidates` (numbers read from pp.1-3, unverified) |
| **VERSION** | A corrected, amended or re-issued rendition of the *same* judgment whose wording differs (a corrigendum or a "CORRECTED" re-issue). Versions stay one judgment. | `version_role` |
| **SOURCE_RENDITION** | The kind of copy. `OFFICIAL_COURT_PDF` is a PDF generated by the court's system; here it is obtained through the open-data mirror, whose host is recorded in the metadata `source_url`. `OFFICIAL_SYSTEM_TEXT` is a court-issued text or HTML rendering; none of the 3,959 copies is one, and `data/text` is our own extraction, not official. `REPORTER_COPY_SCR_MIRROR` is a Supreme Court Reports page range. `SECONDARY_COPY` is a third-party mirror. | `rendition_class` |

The relations between these entities:
- a JUDGMENT has one or more DOCUMENT_COPYs (`copy_identity_role`: SOLE, REPRESENTATIVE or ADDITIONAL);
- a JUDGMENT disposes of one or more PROCEEDINGs;
- a DOCUMENT_COPY may hold more than one JUDGMENT (a composite file) or more than one VERSION.

**Merge rule.** Text alone never merges files. A judgment entity is a connected set of files linked by one of three kinds of evidence:
- identical extracted text, confirmed at byte or render level;
- an identical letter sequence *and* an identical sequence of multi-digit numbers once clock times are removed, with the same court, decision date and page count;
- an incomplete copy whose readable first page matches (similarity of at least 0.95) a file of the same court, date and page count.

Empty or near-empty text never counts as identical content.

## 2. Same-text groups (`SAME_TEXT_GROUPS.csv`)

**Reproduction.** Grouping the batches by `text_sha256` gives **62 groups covering 292 files**, exactly the earlier
finding (E2-10). No group has empty text: the smallest group text has 1,222 characters. Recomputing the text layer
from the bytes reproduced `text_sha256` for all 3,944 files that open.

The evidence for each group was compared with its lowest-sha copy:
- byte comparison in four tiers:
  - bytes identical after masking generation metadata (timestamps, XMP IDs, trailer /ID, xref offsets);
  - the same base revision up to the first `%%EOF`;
  - identical page content streams and images;
  - identical page renders at 40 dpi;
- text quality: the readable-word ratio;
- metadata: court, date, case numbers, and whether each metadata case number appears in pp.1-3;
- PDF producer, page counts, the number of `%%EOF` markers, and composite flags.
