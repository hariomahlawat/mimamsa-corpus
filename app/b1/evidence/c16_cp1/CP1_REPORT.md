## 2. Alignment changes (PR #82 clarifications)

### B01 (site importer)
- **One accounting register (clarification 1).** The signed declaration is `registers/source_accounting.json`
  (`source_admission_accounting`, scope `DECLARED_BY_BUILD`), checked with `mimamsa_contract.c16.accounting.accounting_issues`
  (schema, R1–R7); the site's recomputation (scope `RECOMPUTED_BY_SITE`) is written to
  `<generation>/registers/source_accounting.site.json` and compared with `accounting.compare_declared`. Both digests are in
  `generation.json` `c16.accounting` and in the import report. Fields `provenance`, `effective_admissions`, `by_decision`,
  `not_served_reasons` and `scope` added; `candidate_sha256` replaced by `provenance.candidate_set_sha256`. The private
  `reconcile_accounting` and the use of `legacy.accounting_issues` are removed. The site recomputes the C16
  `generation_manifest_sha256` from the bundled `GENERATION.json` and refuses a declaration that differs.
- **INTEGRITY_REGISTER files** (frozen 2.0 namespace `registers/`) are no longer treated as receipt-artefact candidates.
- **Accelerators travel with the generation.** With a `KNOWLEDGE_RELEASE.json`, the validated manifest and every
  ACCELERATOR component file (re-hashed against the signed inventory) are materialised into the generation, so B03 can
  load the rows and B04 can adopt the text store.
- **`stage_only` import** (CP-1 integration need): the generation is written completely but `ACTIVE` is left to the
  activation journal; recovery neither resumes nor quarantines it.
- Tests: accounting negatives for site widening, decision mismatch, generation pin, V7 candidate-set digest, scope and
  missing candidate set; stage-only import.

### B02 (build skeleton)
- Emits the 2.1 register `registers/source_accounting.json` (replacing `admission-accounting.json`) with the new source ids
  (`c16:<generation>`, `v1:hf:<repo>@<rev>`), field names and provenance; R1–R7 enforced at S4 and recomputed byte-equal at S9.
  v7 is not an input of this build and local uploads are never declared (R7), so neither is listed.
- Lists every `corpus-v2/` and `registers/` file in `RELEASE.json` as kind `other` (the B01 transport rule; before this
  the B01 importer refused B02's bundle with `C16_TRANSPORT`).
- Every component digest uses `mimamsa_contract.c16.digests`: KNOWLEDGE_ROWS now has the final LF
  (`table_rows_digest`), ORIGINALS/TEXT_DERIVATIVES `hashset_digest`, RECORDS/registers `concat_digest`, LEXICAL_INDEX and
  TEXT_STORE `file_digest`, GRAPH cross-checked: `GraphStore.Digest` must equal `digests.graph_digest` over the shipped rows.
  Tested against `v2_1/digests/golden.json`.
- `graph_nodes`/`graph_edges` stay under GRAPH (I-2) and `knowledge_rows.manifest_table_owner_issues` runs in the
  assembler's manifest check.
- **TEXT_STORE ships prebuilt** with the bundle-independent 2.1 source digest (was SITE_BUILDS_CHEAP); S9 checks the
  shipped digest equals a fresh site's and that a fresh rebuild is byte-identical.
- New `cp1` fixture exchange (real bytes from the B01 producer harness, receipts bound to the committed register) and
  `specs/cp1-slice.spec.json`; a test pins it. Ordered inventories use the ordinal `/`-path order (B01's c006d300
  finding); a mixed-case test asserts it for SHA256SUMS, component file lists and concat digests.

### B03 (knowledge rows)
- `.NET` KNOWLEDGE_ROWS component digest checked against `golden.json` (`C16DigestTests`), including that the no-final-LF
  value differs. The 2.1 loader grants (USAGE + INSERT only; the activator creates staging) are kept as built.
- New integration domain `KnowledgeActivationDatabase` (B03 + B06): B06's DB_APPLIED promotes `kr_<n>_staging` and points
  every `knowledge` view at `kr_<n>` in one transaction, with the B06 `knowledge_head` view and publication row; recovery
  and rollback re-point idempotently.

### B04 slice (text store)
- `DiskTextStore.SourceDigest` is now `digests.text_store_source_digest` (bundle-independent; no `generation.json` and no
  SHA256SUMS in the preimage); golden-tested (`TextStoreSourceDigestEqualsThePythonGolden`). `Bind()` is unchanged.
- A store shipped with the generation is **adopted** (copied, fully verified, atomically published) when its 2.1 digest
  equals the site's and both files hash to the signed inventory; otherwise the site builds. Option
  `TextStoreOptions.AdoptShipped` (default on; the central build turns it off so it always rebuilds).
- Every text-store test rerun in both default and `MIMAMSA_TEST_TEXT_STORE=disk` modes, including both `VerifyOnOpen`
  settings: 36/36 each (28 existing + 8 new: two goldens, adoption under both VerifyOnOpen settings, three mismatch cases
  that build instead, and Bind still re-deriving after adoption).

### B06 (activation journal)
- **Ed25519 decision: switched to BouncyCastle.Cryptography 2.6.2** (MIT, pure managed, no native dependency), restored
  from nuget.org. B06's hand-written BigInteger verifier is removed. Key/signature lengths and S < L are still checked
  explicitly. The RFC 8032 vectors and the pyca-signed Python ExclusionStore interop test are kept and pass; test signing
  uses the same library. All 66 activation tests pass.
- Response-boundary filtering wired **behind the flag only** (`AppServices.ActivationExcluded`, null by default): search
  (hits removed before paging, totals reduced, facet counts withheld when anything was removed), document, document text,
  citation and permalink (`/api/cite`) each filter by the **current** signed exclusion state for the request's pin; an
  unreadable store withholds (fail closed).
- `GenerationStore.Load(..., generationId)` (default unchanged) so a staged generation can be verified before activation.

## 3. The slice and its outputs

One driver, `app/b1/build/c16_cp1_slice.py run`, plus one C# journey, `C16Cp1SliceTests` (runs only when the driver sets
`MIMAMSA_CP1_CONTEXT`). Steps:

1. **B02** builds two development-signed degraded releases: G1 = `R16-cp1-fixture-20261127-00000001` (2.0 positive
   exchange + SYN v1 corpus) and G2 = `R16-cp1-slice-20261128-00000002` (2.1 exchange with real bytes: copy A admitted
   with nine typed receipts and also a v1 document; B held; E eligible but C16-only). Both pass S0–S9; S9's expected
   outcome is ACTIVE_DEGRADED.
2. **B01** imports G1 into a fresh isolated site (signed exclusion channel; real Python ExclusionStore with a development
   register key) and imports G2 **stage-only**.
3. **B03** creates `c16cp1_src_*`, seeds it through the app's stores, clones it with `CREATE DATABASE … TEMPLATE`, runs
   the I-3 migration on the **clone** (13 tables copied and verified; `public` dump unchanged), creates the restricted
   loader role, and loads both generations' knowledge rows **and graph rows** through the one typed loader (typed parse,
   COPY as the loader, counts, digests, full re-derivation): kr_1 = 5 row tables + graph_nodes 18 / graph_edges 5,
   kr_2 = 5 row tables + graph_nodes 19 / graph_edges 5.
4. **B04** adopts each shipped text store (no rebuild; equal to the memory reference) and checks the lexical index file
   (SHA-256 against the inventory, `quick_check`).
5. **B06** stages both generations, initialises the journal on G1 (views on `kr_1`) and, with
   `Mimamsa:Activation:Enabled=true` in a real Kestrel process over the authenticated control channel and a PostgreSQL
   advisory lock, **activates G2**: DB_APPLIED promotes `kr_2` and repoints the views. The old process fails closed (503);
   the restarted one adopts the shipped text store itself and serves G2.
6. **Outcome**, computed by the driver with the reference `components.activation_outcome` over what the site verified:
   `ACTIVE_DEGRADED`, `DEGRADED_LEXICAL_ONLY`, `site_embedding: NEVER`; reasons: vectors missing (lexical-only), uncalibrated
   sampled checks recorded (development mode). Search runs lexical with semantic "not part of B1"; no embedder is
   configured (embedder calls 0).

Checks (all pass; 45 in the journey, list in `slice-evidence-local-windows.json`):
- **Only admitted or independently established copies are visible:** A is found by search and its text, citation and
  permalink (`CITED_COPY_ELIGIBLE`) serve; held B and C16-only E return 404 and never appear in search; SYN legacy copies
  serve; G1 never had A.
- **Exclusion after activation, enforced at the response boundary without a restart:** a withdrawal of A appended with the
  real Python ExclusionStore under B06's exclusion-acceptance guard is applied to every installed generation; then
  document, text, citation and permalink of A return 404, search no longer returns A, other copies still serve.
- **Rollback:** a journaled ROLLBACK to G1 repoints the views to `kr_1` and ACTIVE to G1; the running process fails closed;
  the restarted one serves G1.
- **Oracle unaffected in default mode:** the PR #54 retrieval oracle (unmodified), with activation off and memory/memory,
  gives exactly the established hybrid-off baseline (10/14; RET-06/07/09/10 expect hybrid mode and fail identically in
  every earlier oracle-off run): `oracle-default-mode-local-windows.txt` is line-for-line identical to
  `c16_text_store/raw/oracle-disk/oracle-off.txt`.
- Cleanup: every `c16cp1_*` database and role is dropped by the journey.

## 7. Remaining gaps and flags for review

1. ~~v7 candidate hashes~~ **Resolved (§8):** PR #82 `9af665e7` specified CS1–CS5; B01 and B02 use the reference check.
2. ~~B06 needed a model "with vectors for" a lexical-only target~~ **Resolved (§8):** M1/M2/K1/K2 with null MODELS; the
   slice activates with NO model; the placeholder model is gone.
3. ~~The importer wrote ACTIVE itself; the journey wrote the catalogue marker~~ **Resolved (§8):** `stage_only` is
   mandatory on journal-managed sites; `GenerationStaging` (Core, activation tool) writes the marker.
4. **No in-process generation swap**: after OPEN the web process fails closed until restarted (B06's design for CP-1).
5. **B04 .NET verifiers** (graph structural recheck, sampled rebuild parity, postings and query parity) are not built;
   GRAPH and KNOWLEDGE_ROWS are verified by the loader's full re-derivation; LEXICAL_INDEX only by file hash and
   `quick_check`; LEXICAL_INDEX is still rebuilt by the app at start (not adopted).
6. **Search facet counts** are withheld when the boundary removes a result (recomputing them needs the engine).
7. **Graph surface, Studio and PDF delivery** are not yet behind the response-boundary filter (CP-1 scope was search,
   document text, citation and permalink).
8. **Load-dependent test flakes seen locally** (each passed in isolation and in a later full run):
   - B06 `ControlChannelTests` (the not-lock-holder rejection and the authenticated-pipe switch): a race in the tests
     (the client's channel timeout could fire before the server recorded the rejection). **Fixed by the B06 author**
     (`7906efbe`, merged); not seen again.
   - `TextStoreTests.ADerivativeRemovedOrCorruptedAfterTheBuildIsNotServedAfterReopen(corrupt, True)`: one failure in a
     disk-mode full run on the follow-up head; passed 3/3 in isolation and in the full rerun. The 2.1 digest change does
     not alter this case's path (a corrupted derivative file never changes the records, before or after).
   - `PersistentIndexTests.ARebuildReusesCachedTokensAndGivesIdenticalResults`: one failure in the disk-mode full suite;
     not reproduced in 3 isolated runs and 1 further full run. The known `DiskEngineReturnsExactlyWhatTheMemoryEngineReturns`
     did not fail in any run here.
9. **Disposable objects outside `c16cp1_`**: running the full B1 suite creates and drops the streams' own `c16b03_*` and
   `c16b06_*` databases/roles (their tests' fixed prefixes). All were dropped.
10. **Scale**: accelerator files are read into memory by the importer for materialisation (fine for fixtures; B09 must
    stream them).
11. `mimamsa_contract.devbundle` (v1) still sorts `Path` objects when writing SHA256SUMS (B01's c006d300 finding). The CP-1
    path does not use it (B02 writes its own ordinal inventories), so it is left unchanged and reported.
12. **For PR #82 (interfaces):** `app/contract/fixtures/c16/v2_1/.gitattributes` marks only `*.json` and `*.jsonl` as
    `-text`. The new `.txt` candidate-set fixture is therefore converted to CRLF on `core.autocrlf=true` checkouts
    (Windows), so two interface tests fail there (CS2 digest, fixture byte-identity). Linux CI is unaffected. Fix: add
    `*.txt -text` in the interface branch. Not changed here.
13. **v7 in a real build:** B02 reads v7 candidate sets from the pinned revision at `v7/candidate_sets/<name>.txt` (canonical
    bytes, refused otherwise). The real layout of `legal_knowledge/candidates/cycle15/v7` still needs converting into that
    form in Stage 3 (like the v1 canonical layout).

## 8. CP-1 follow-up (PR #82 `9af665e7`: CP-1 gaps specified as additive 2.1 rules)

- **Merges:** interfaces `9af665e7`; B06 `7906efbe` (channel-test races) and `81b9253f` (lexical-only releases), the latter
  also merged by the B06 author (`4d54108b`); both resolutions of the one `Program.cs` conflict keep both the B06
  per-pin semantic gate and the CP-1 response boundary (identical content).
- **B01 candidate sets:** the private check is removed. `accounting.candidate_set_issues(declared, files,
  admission_inventory)` (CS1–CS5) runs on the signed declaration against the ADMISSION_REGISTER inventory (the signed
  RELEASE.json inventory when the bundle has no knowledge release manifest); the verified union feeds
  `legacy.legacy_issues` as `candidate_shas`. Tests: missing file (CS1), digest (CS2), orphan (CS5). The B01 test harness
  ships a candidate set only when its declaration declares the V7 source, as CS5 requires.
- **B02 candidate sets:** every declared `V7_REFERENCE` source (read from `v7/candidate_sets/<name>.txt` at the pinned
  revision) ships `registers/candidate_sets/<name>.txt` (sorted lower-case hex, LF-joined, no final LF, ASCII; sha256 =
  `provenance.candidate_set_sha256`; lines = `input`) in the ADMISSION_REGISTER files, SHA256SUMS and the signature. S2's
  SG-1 relabel check uses the hashes, and S9 runs the reference check against the signed inventory. The cp1 mirror carries
  `v7:cycle15`, so the slice imports a V7_REFERENCE source end to end.
- **Lexical-only activation with NO model:** `GenerationStaging` records B06's lexical-only classification (from the
  verified `KNOWLEDGE_RELEASE.json`) with the catalogue marker; the journal is initialised with `models = null`; G2 is
  activated and G1 rolled back to under K2 with no model installed (`b06_no_model_installed`). Search runs lexical-only.
  The outcome is still ACTIVE_DEGRADED / DEGRADED_LEXICAL_ONLY with `site_embedding: NEVER`.
- **`stage_only` mandatory on journal-managed sites:** once `journal/journal.jsonl` or `activation-state/SITE_INIT.json`
  exists, a non-stage import is refused before anything is written (`ACTIVATION_JOURNAL_MANAGED`); tested with the site
  byte-identical.
- **Catalogue marker owner:** `Mimamsa.Core.Activation.GenerationStaging.VerifyAndStageAsync` (the activation tool's
  staging step) runs the B03 restricted loader (knowledge and graph rows), the B04 text-store adoption and lexical-index
  checks, and writes `C16_VERIFIED.json` last and only when all pass. The journey calls it and asserts the generation is
  not installed before it. Wiring it into the `Mimamsa.Activation` CLI (a `stage` command with the loader's credentials)
  is B07 installer work.
