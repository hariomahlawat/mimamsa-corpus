## 3. Serving and recovery · condition on R2-N01

R3's T0 model is implementable in principle. A single native Windows service can own policy and protected transport, accepting exact immutable byte prefixes into a finite one-way queue under the same coordinator that serializes durable policy changes. The prepared suffix remains behind the policy gate. The accepted prefix may drain after withdrawal, even if the client has not yet received it. Framework buffering and proxy/TLS/kernel semantics determine whether a particular implementation satisfies that contract. T1/IIS is eligible only if every downstream protected path is inside the audited boundary or is a proven one-way sink. The protocol rejects a plain framework Write/Flush return, deferred file descriptor or reusable URL as evidence of acceptance. Writer priority, deadlines and a stated p95 ≤1 s / maximum ≤5 s proposal give the PoC a concrete workload target without making an unmeasured production claim. [Serving §§6/9](https://github.com/hariomahlawat/mimamsa-corpus/blob/05cd3bf7eb1b782db26187077633f14944dc4acd/docs/architecture/intelligence/SERVING_AND_REVOCATION_CONTRACT.md#L78-L123) · [Observer requirements](https://github.com/hariomahlawat/mimamsa-corpus/blob/05cd3bf7eb1b782db26187077633f14944dc4acd/docs/architecture/intelligence/SERVING_AND_REVOCATION_CONTRACT.md#L157-L159)

**Credit across parallel handoffs.** The proposed API checks remaining credit and accounts actual acceptance afterwards under a guard described as shared. A writer-priority read/write guard excludes revocation from byte handoff, but permits two readers to see the same remaining site credit before either charges it. For example, with 64 KiB available, two requests for 64 KiB could both pass that check. The explicit ambiguous-transfer branch also closes the connection without specifying how many uncertain bytes remain charged. These affect the residual-byte promise and recovery under backpressure. They do not undo the specified ordering of any actual handoff against the fence. For the PoC, serialize credit check, reservation, acceptance and settlement with a single admission loop, or atomically reserve requested credit before parallel adapter calls. Charge the accepted prefix, return only known unused reservation, and retain a conservative charge on ambiguous transfer until independently established drain/termination. Report unique accepted payload and physical downstream buffering separately. Extend REV-02/07 with simultaneous contenders at the site and connection limits, partial acceptance, ambiguous return, slow drains and writer progress. Compare an independent transport observation with the charge ledger and fence. [Guard and adapter sequence](https://github.com/hariomahlawat/mimamsa-corpus/blob/05cd3bf7eb1b782db26187077633f14944dc4acd/docs/architecture/intelligence/SERVING_AND_REVOCATION_CONTRACT.md#L84-L111)

**Large-PDF entry path.** The HTTP contract specifies exact 206 ranges, current authorization before response metadata, no stale 304 or protected cache, and prohibition of unsafe full-response fallback. A stock PDF.js URL fetch can open with an ordinary request and discover range support from response headers before issuing a range request. Simply setting a range chunk size does not guarantee an acceptable initial request to this profile. Use the selected client's supported bounded path, for example authorized metadata with a PDF.js range adapter. Extend P4/REV-02 to open and navigate an original larger than the full-response cap, including a jump near the end, from a fresh session. Verify real request sizes, response ranges and authorization before headers, then withdraw between chunks. Require a useful bounded viewer for eligible originals and appropriate termination/refresh on withdrawal. Small files, invalid ranges and conditional requests need separate positive and negative cases. This condition keeps the ordinary viewer usable while preventing unverified transport fallback. [Protected HTTP contract](https://github.com/hariomahlawat/mimamsa-corpus/blob/05cd3bf7eb1b782db26187077633f14944dc4acd/docs/architecture/intelligence/SERVING_AND_REVOCATION_CONTRACT.md#L113-L123) · [PDF.js URL and range fetch paths](https://github.com/mozilla/pdf.js/blob/98100629a8ab3c6625c82a5ab5b9a82457f415f3/src/display/fetch_stream.js#L84-L176) · [PDF.js custom range API](https://github.com/mozilla/pdf.js/blob/98100629a8ab3c6625c82a5ab5b9a82457f415f3/src/display/api.js#L116-L123)

**Effective state and durability.** R3 distinguishes a release-only withdrawal from a signed site-wide suppression and a local channel withdrawal. Component-vector CAS and recomputation prevent replacement by a stale staged snapshot. In the REV-04/08 fixture, preserve the re-admission requirement even when a signed complete list drops an exclusion and the source still has an older publication record. Treat the re-admission requirement as part of applicable denial until the authorised exact-scope decision. Counts or adverse-authority coverage must revalidate even when displayed hits do not change. P0 makes recoverable bytes durable. P1 commits the matching digest via independent witness CAS. P2 reconstructs before serving. P3 acknowledges with the operation identity. This is a concrete recovery state machine. Test the witness remaining current when the DB and journal roll back, crash after CAS before the acknowledgment, authenticated repeat acknowledgment, mismatched digest, and loss of witness custody alongside matched old snapshots. Any unknown current authority halts protected access. Actual flush guarantees, custody and recoverability on the selected storage remain P8 and deployment proof. [Serving §§7–9](https://github.com/hariomahlawat/mimamsa-corpus/blob/05cd3bf7eb1b782db26187077633f14944dc4acd/docs/architecture/intelligence/SERVING_AND_REVOCATION_CONTRACT.md#L125-L159)
