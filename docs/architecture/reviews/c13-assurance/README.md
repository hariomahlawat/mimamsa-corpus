## 4. How to interpret and record results

Use one record per test case, environment and result, with the following values. Derive expected results before executing and retain separate expected and observed values.

| Field | Required record |
|---|---|
| Test ID and capability | Stable ID from this package, capability and cited requirement/revision |
| Fixture and oracle | Fixture identifier and immutable digest, expected and prohibited outcomes, independent oracle version and rationale |
| Executed environment | Exact repo/tree/adapter hashes, command or observed journey, host/OS/runtime/filesystem/browser, workload, relevant config hashes and provenance of the observation |
| Actual | Result status and observed output, raw evidence location and measurement limits; preserve timing units, sample size and error cases |
| Acceptance | Scope the result proves, open dependency and additional evidence required; recorded independent reviewer and date |

- **Passed** means this exact input ran against the identified executable or observation and matched its oracle within that scope.
- **Failed** means executed on the applicable implementation or exercising an oracle and observed a mismatch. Preserve the evidence and direct affected scope.
- **Blocked** means a known dependency such as the selected Windows host or test custody stops valid execution.
- **Not implemented** means the application interface needed for the case is absent at the pinned commit.
- **Not executed** means the test exists or is specified and evidence was not collected. Explain why.
- **Not applicable** means the requirement does not apply to the particular host/phase/operation. Document the reason. It cannot clear a requirement in the deployment that needs it.

Report actual counts by status and evidence set. A skipped case never enters the pass denominator. Keep statically inspected behavior and inference distinct from executable observations. Technical acceptance cannot establish legal applicability, approval, or authority.

**Reference oracles.** For source identity use independent SHA-256 over exact fixture bytes and original physical-page IDs. For producer transformations use a labelled admissibility mapping and permitted loss, rather than treating the source schema validator as an adapter. For search and UX use independently labelled relevance, material adverse evidence and objective journey completion with accessibility observation. For transport use the independent acceptance event and durable fence, separate from later drain/client receipt. For access control use before/after state, actual surfaces and synthetic canaries. Development examples in this PR are public to developers. The blind application holdout, with answers held separately, is not included. See the linked test specifications for commands and fixture details.

### Executable now

Use Python 3.12 with the pinned R1 dependencies when invoking an R1 or producer check. Fetch the above commits through normal repository access. Point the harnesses at the local pinned Git objects and code-only snapshots. Use an isolated evidence workspace. No corpus download is necessary for these commands.

```sh
python -B data_oracle.py --repo /path/to/repository-with-pinned-objects
python -B platform_oracle.py --contract-dir /path/to/pinned/app/contract
python -B backup_oracle.py --backup-script /path/to/pinned/scripts/backup_corpus.py
python -B retrieval_oracle.py --self-test
python -B transport_oracle.py --self-test
python -B transport_oracle.py --reference /path/to/repository-with-reference-commit
```

The data probe preserves expected reference acceptances, rejections and gaps. Its successful process exit means the observations matched the pinned baseline, including mismatches to the future end-to-end requirements. The retrieval scorer accepted 14 ideal observations and rejected eight negative controls. The independent transport trace oracle accepted one valid vector and rejected 16 inconsistent variants. The Linux black-box HTTP run used two exact bounded ranges, 13 pre-withdrawal denial controls and three fresh post-withdrawal denials. The platform oracle passed three checks and the corpus backup verifier passed five synthetic cases. No real search ranking, site ingestion, storage-backed fence, Windows production transport or participant UX evidence was generated by these commands.
