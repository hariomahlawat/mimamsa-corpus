# Security, recovery and platform acceptance

These fixtures describe defensive acceptance in an isolated disposable app instance with generated content and test identities. No endpoint, deployment, parser or credential beyond the pinned PoC and R1 is presumed. Record independent observations of authorized and denied routes, outputs, artifact existence after restart, process/resource counters and filesystem state. Keep injected markers and real source data out of telemetry beyond the dedicated synthetic capture.

Run the portable checks with the pinned R1 Python dependencies:

```sh
python -B platform_oracle.py --contract-dir /path/to/pinned/app/contract
```

Observed here on Linux x86-64 with Python 3.12.14, **3 passed**. The tests are portable baseline assurance and do not establish Linux production support or Windows ACL, driver, buffer or service behavior. The separate implementation branch's hosted Windows/Linux jobs exercise a reference transport only. [Hosted reference CI](https://github.com/hariomahlawat/mimamsa-corpus/actions/runs/45638259239)

### Executable corpus backup verification controls

Run `python -B backup_oracle.py --backup-script /path/to/pinned/scripts/backup_corpus.py` with that snapshot's adjacent `restricted_material.py`. The harness calls only the offline `verify` subcommand, generates all bytes under a temporary directory, and never accesses a corpus repository. All five cases below exercise **SEC-10**, Cycle 13 §31, and apply only to the corpus helper. The independent oracle fixes exit code, hash-failure count and unexpected-file count respectively. Any different tuple is prohibited.

| ID | Input fixture | Expected tuple | Actual on Linux 3.12.14 | Remaining acceptance evidence |
|---|---|---|---|---|
| BKP-01 | Two originals, one SHA-256 content identity and one Git blob identity | (0, 0, 0) | **Passed** (0, 0, 0) | Owner storage restore and current site policy |
| BKP-02 | One same-size byte change | (1, 1, 0) | **Passed** (1, 1, 0) | Native Windows storage and stable source identity |
| BKP-03 | One missing manifest entry's file | (1, 1, 0) | **Passed** (1, 1, 0) | Full storage recovery |
| BKP-04 | One unexpected benign file | (1, 0, 1) | **Passed** (1, 0, 1) | Live exclusion and independent filesystem inventory |
| BKP-05 | Manifest records one creation-time mismatch | (1, 1, 0) | **Passed** (1, 1, 0) | Actual corpus backup creation under authorized custody |

The helper's offline verification attaches to bytes declared in its provided manifest. Site policy freshness and manifest provenance still require separate trusted evidence.
